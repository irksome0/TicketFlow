# Чернетка виправлених розділів дипломної роботи TicketFlow

## РОЗДІЛ 3. ПРОГРАМНА РЕАЛІЗАЦІЯ СИСТЕМИ

У цьому розділі описано програмну реалізацію вебсистеми управління запитами клієнтів у сервісі з надання IT-послуг TicketFlow. Основну увагу приділено структурі серверної та клієнтської частин, реалізації REST API, організації доступу до бази даних, механізмам автентифікації, рольового розмежування доступу, обробці вкладень та відображенню функціональних можливостей у вебінтерфейсі.

Реалізована система побудована за клієнт-серверною архітектурою. Серверна частина відповідає за обробку HTTP-запитів, автентифікацію користувачів, перевірку прав доступу, виконання бізнес-логіки, збереження даних у PostgreSQL та роботу з файлами вкладень. Клієнтська частина реалізує вебінтерфейс користувача, взаємодіє з backend через REST API та забезпечує рольово-залежне відображення функцій системи.

### 3.1. Реалізація серверної частини

Серверну частину системи TicketFlow реалізовано мовою програмування Go із використанням вебфреймворку Gin. Для роботи з базою даних PostgreSQL застосовано ORM-бібліотеку GORM. Такий підхід дозволяє поєднати продуктивність Go, простоту побудови HTTP API та зручність опису моделей предметної області у вигляді структур мови програмування.

Backend-проєкт має модульну структуру, що розділяє відповідальність між окремими частинами системи:

- `cmd` - точка входу до застосунку;
- `internal/config` - завантаження конфігурації з environment variables;
- `internal/database` - ініціалізація підключення до PostgreSQL та виконання міграцій;
- `internal/models` - опис основних сутностей предметної області;
- `internal/repository` - доступ до даних через GORM;
- `internal/handlers` - HTTP-обробники REST API;
- `internal/middleware` - middleware для JWT-автентифікації та перевірки ролей;
- `internal/router` - реєстрація маршрутів API.

Основними моделями backend-частини є `Organization`, `User`, `Ticket`, `TicketComment`, `Attachment`, `OrganizationInvite` та `TicketStatusHistory`. Модель `Organization` використовується для реалізації багатоклієнтності, оскільки користувачі, заявки та пов'язані з ними об'єкти логічно належать до конкретної організації. Такий підхід забезпечує ізоляцію даних між різними клієнтами системи.

Модель `User` містить ідентифікатор організації, email, хеш пароля, роль користувача, ім'я, прізвище та службові часові поля. Паролі не зберігаються у відкритому вигляді: перед записом до бази даних вони хешуються за допомогою bcrypt. Це знижує ризик компрометації облікових даних у разі несанкціонованого доступу до бази даних.

Модель `Ticket` описує заявку клієнта та містить такі основні поля: заголовок, опис, статус, пріоритет, автор, організація, можливий виконавець, дата створення, дата вирішення та дата оновлення. Для контролю SLA використовуються часові мітки `created_at`, `resolved_at`, пріоритет заявки та історія зміни статусів. SLA-engine обчислює активний час виконання не як просту різницю між датами, а з урахуванням робочого календаря, вихідних днів, святкових дат і паузових статусів.

Для фіксації історії зміни станів заявки використовується модель `TicketStatusHistory`. Вона зберігає попередній статус, новий статус, користувача, який виконав зміну, та час зміни. Наявність такої історії підвищує прозорість опрацювання заявок і дозволяє обґрунтовано розраховувати активний час виконання звернення.

### 3.2. Реалізація автентифікації та рольового доступу

Автентифікація користувачів у системі реалізована на основі JWT. Після успішного входу користувач отримує токен, який надалі передається у заголовку `Authorization` у форматі `Bearer <token>`. Middleware серверної частини перевіряє коректність токена, отримує ідентифікатор користувача, його роль та ідентифікатор організації, після чого записує ці дані в контекст запиту Gin.

У системі реалізовано чотири ролі користувачів:

- `Client` - створює заявки, переглядає власні заявки, додає вкладення, закриває та повторно відкриває власні звернення;
- `Operator` - переглядає заявки організації та виконує первинне опрацювання звернень;
- `Engineer` - опрацьовує заявки, змінює їхні статуси та додає вкладення в межах своєї організації;
- `Admin` - керує користувачами та їхніми ролями в межах організації.

Розмежування доступу реалізовано як на рівні маршрутів, так і на рівні окремих handler-ів. Наприклад, адміністративні маршрути керування користувачами доступні лише користувачам з роллю `Admin`. Водночас операції з вкладеннями недоступні адміністратору, оскільки в межах зафіксованих вимог ця роль відповідає за управління користувачами, а не за роботу з файлами заявок.

Особлива увага приділена захисту від IDOR-вразливостей. Перед переглядом або зміною заявки сервер перевіряє, чи належить заявка до організації поточного користувача. Для користувача з роллю `Client` додатково перевіряється, чи є він автором відповідної заявки. Це унеможливлює доступ клієнта до заявок інших користувачів або інших організацій навіть у разі підміни ідентифікатора в URL.

### 3.3. Реалізація управління заявками

Управління заявками реалізовано через REST API. Користувач може створювати заявку, отримувати список заявок, переглядати деталі конкретної заявки та змінювати її статус відповідно до дозволених переходів.

Основні endpoint-и для роботи із заявками:

- `GET /api/v1/tickets` - отримання списку заявок;
- `POST /api/v1/tickets` - створення нової заявки;
- `GET /api/v1/tickets/:id` - отримання деталей заявки;
- `PATCH /api/v1/tickets/:id/status` - зміна статусу заявки.

Під час створення заявки backend перевіряє обов'язкові поля, зокрема заголовок, опис та пріоритет. Нова заявка автоматично отримує статус `New`, ідентифікатор організації поточного користувача та ідентифікатор автора. Такий підхід гарантує, що користувач не може самостійно підставити чужу організацію або створити заявку від імені іншого користувача.

Життєвий цикл заявки обмежується визначеними переходами між статусами. У системі використовуються статуси `New`, `In Progress`, `Pending`, `Waiting for Customer`, `On Hold`, `Resolved`, `Closed` і `Reopened`. Перехід до нового статусу виконується лише після перевірки поточного стану заявки, ролі користувача та допустимості цільового статусу. Статуси `Pending`, `Waiting for Customer` і `On Hold` використовуються для призупинення SLA-лічильника, коли подальша робота залежить від додаткової інформації, зовнішніх умов або відповіді клієнта. У разі переходу в статус `Resolved` встановлюється поле `resolved_at`, а під час повторного відкриття заявки воно очищується для нового циклу опрацювання.

### 3.4. Реалізація роботи з вкладеннями

У системі передбачено можливість додавання вкладень до заявок. Це дозволяє клієнту або технічному персоналу передавати додаткові матеріали, наприклад скріншоти, текстові файли, журнали помилок або PDF-документи.

Backend реалізує три основні операції з вкладеннями:

- `POST /api/v1/tickets/:id/attachments` - завантаження файлу;
- `GET /api/v1/tickets/:id/attachments` - отримання списку вкладень заявки;
- `GET /api/v1/tickets/:id/attachments/:aid/download` - скачування вкладення.

Перед збереженням файлу система перевіряє його розмір, розширення та належність заявки до організації поточного користувача. Дозволеними форматами є `jpg`, `jpeg`, `png`, `pdf`, `txt` і `log`. Ім'я файлу очищується за допомогою базового імені файлу, після чого формується унікальний шлях з використанням UUID. Локальний шлях збереження має структуру:

`uploads/{organizationID}/{ticketID}/{attachmentID}_{originalFileName}`

У базі даних зберігаються лише метадані вкладення: ідентифікатор, заявка, користувач, оригінальна назва файлу, шлях збереження, розмір, MIME-тип і дата створення. Binary-вміст файлу не зберігається в PostgreSQL, що відповідає практиці розділення структурованих даних і файлового сховища.

Перед скачуванням вкладення backend повторно перевіряє JWT, роль користувача, належність заявки до організації, право клієнта на доступ до власної заявки та відповідність вкладення конкретній заявці. Після успішної перевірки файл повертається клієнту через backend API. Такий підхід є безпечнішим, ніж використання публічних посилань на приватні файли.

### 3.5. Реалізація управління користувачами

Для адміністратора реалізовано функції керування користувачами в межах організації. Backend надає endpoint-и для перегляду списку користувачів, зміни ролі користувача та створення запрошення до організації.

Основні endpoint-и:

- `GET /api/v1/users` - отримання користувачів організації;
- `PATCH /api/v1/users/:id/role` - зміна ролі користувача;
- `POST /api/v1/users/invites` - створення запрошення користувача;
- `GET /api/v1/users/invites/:token` - отримання інформації про запрошення;
- `POST /api/v1/users/invites/:token/accept` - прийняття запрошення та створення облікового запису.

Запрошення містить email користувача, роль, строк дії та хеш токена. Сам токен не зберігається у відкритому вигляді, що знижує ризик його несанкціонованого використання. Після прийняття запрошення створюється користувач у відповідній організації.

### 3.6. Реалізація клієнтської частини

Клієнтську частину системи реалізовано на основі Next.js, React і TypeScript. Для стилізації використовується Tailwind CSS. Застосунок побудований із використанням App Router, що дозволяє організувати сторінки відповідно до функціональних розділів системи.

Основні сторінки frontend-частини:

- `/login` - вхід користувача;
- `/register` - реєстрація організації та адміністратора;
- `/register/invite/[token]` - прийняття запрошення користувачем;
- `/tickets` - список заявок;
- `/tickets/new` - створення заявки;
- `/tickets/[id]` - детальний перегляд заявки;
- `/users` - управління користувачами для адміністратора.

Для взаємодії з backend створено централізований API-клієнт у файлі `lib/api.ts`. Він отримує базову адресу API з environment variable `NEXT_PUBLIC_API_URL`, додає JWT до захищених запитів, обробляє JSON-відповіді та підтримує multipart-запити для завантаження вкладень. Для скачування файлів використовується `fetch` із заголовком `Authorization`, після чого відповідь перетворюється на `Blob` і передається користувачу як файл.

Типи даних, що використовуються у frontend, винесено до `lib/types.ts`. Це дозволяє уніфікувати роботу з сутностями `User`, `Ticket`, `Attachment`, `Invite`, `AuthResponse` та іншими структурами, а також зменшує ризик помилок під час інтеграції frontend і backend.

### 3.7. Реалізація контролю SLA

Контроль SLA у системі реалізовано як окремий SLA-engine на backend-рівні. Його призначення полягає в тому, щоб визначати допустимий строк опрацювання заявки не лише за різницею між `created_at` і `resolved_at`, а з урахуванням робочого календаря та життєвого циклу звернення. Для кожної заявки визначається граничний час виконання залежно від пріоритету:

- `High` - 8 робочих годин;
- `Medium` - 24 робочі години;
- `Low` - 72 робочі години.

Робочий календар задається через конфігурацію backend: часову зону, початок і завершення робочого дня, а також перелік святкових дат. У типовій конфігурації використовується часовий пояс `Europe/Kyiv`, робочий інтервал `09:00-18:00` і робочі дні з понеділка по п'ятницю. Час, що припадає на нічні години, вихідні та зазначені святкові дати, не збільшує активний SLA-лічильник.

SLA-engine використовує історію статусів `TicketStatusHistory`. Активними для SLA вважаються статуси `New`, `In Progress` і `Reopened`, тоді як `Pending`, `Waiting for Customer` і `On Hold` призупиняють відлік. Це дозволяє коректно моделювати ситуації, коли сервісна команда очікує відповідь клієнта або зовнішнє уточнення. На основі цих даних система обчислює активний час, час паузи, залишок SLA, прогнозований дедлайн, момент порушення SLA та підсумковий статус: `Within SLA`, `Paused`, `Met` або `Breached`.

На frontend SLA відображається у вигляді індикатора на сторінці списку заявок і розширеного блоку на сторінці деталей заявки. Користувач бачить активний час, ліміт за пріоритетом, час паузи, дедлайн і використаний робочий календар. Це дозволяє швидко оцінити стан виконання звернення без ручного аналізу часових міток.

### Висновки до розділу 3

У третьому розділі описано програмну реалізацію вебсистеми TicketFlow. Розглянуто структуру backend-частини на Go, реалізацію REST API, моделі бази даних PostgreSQL, механізм JWT-автентифікації, рольове розмежування доступу, роботу з вкладеннями та SLA-engine. Також описано клієнтську частину на Next.js, централізований API-клієнт і рольово-залежні сторінки інтерфейсу.

Реалізована архітектура відповідає предметній області управління клієнтськими заявками в IT-сервісі. Вона забезпечує багатоклієнтність, ізоляцію даних організацій, контроль життєвого циклу заявки, підтримку вкладень і можливість подальшого розвитку системи.

## РОЗДІЛ 4. ТЕСТУВАННЯ ТА ДОСЛІДНА ЕКСПЛУАТАЦІЯ

У цьому розділі наведено підхід до тестування вебсистеми TicketFlow, описано основні сценарії перевірки backend і frontend, розглянуто тестування безпеки, рольового доступу, багатоклієнтності, роботи з вкладеннями та коректності життєвого циклу заявки.

### 4.1. Мета та об'єкти тестування

Метою тестування є перевірка відповідності реалізованої системи функціональним і нефункціональним вимогам, визначеним у попередніх розділах дипломної роботи. Особлива увага приділялась тим функціям, які є критичними для предметної області: автентифікації, ізоляції даних організацій, рольовому доступу, створенню та опрацюванню заявок, контролю SLA і роботі з вкладеннями.

Об'єктами тестування були:

- REST API серверної частини;
- frontend-інтерфейс Next.js;
- інтеграція frontend із backend;
- база даних PostgreSQL;
- механізм JWT-автентифікації;
- рольові обмеження доступу;
- завантаження, перегляд і скачування вкладень;
- контроль переходів між статусами заявки.

Для перевірки backend використовувались автоматичні тести Go, ручні HTTP-запити через Postman або curl, а також перевірка відповідей API. Для frontend виконувалась перевірка збірки застосунку, ручне проходження основних сценаріїв користувача та аналіз поведінки інтерфейсу для різних ролей.

### 4.2. Функціональне тестування

Функціональне тестування було спрямоване на перевірку основних бізнес-процесів системи. До них належать реєстрація організації, вхід користувача, створення заявки, перегляд списку заявок, зміна статусу, додавання вкладення, скачування вкладення та управління користувачами адміністратором.

### 4.4. Тестування багатоклієнтності та захисту від IDOR

Багатоклієнтність є однією з ключових вимог до системи TicketFlow. Для її перевірки було створено користувачів, що належать до різних організацій. Після цього виконувались запити на отримання заявок, деталей заявок і вкладень з підміною ідентифікаторів ресурсів.

Під час тестування перевірялись такі умови:

- клієнт однієї організації не може переглянути заявку іншої організації;
- оператор або інженер працює лише з даними своєї організації;
- адміністратор бачить користувачів лише своєї організації;
- вкладення не можуть бути отримані через підміну `ticketID` або `attachmentID`;
- backend перевіряє відповідність вкладення конкретній заявці.

У результаті перевірки встановлено, що доступ до ресурсів іншої організації блокується на рівні backend. Це підтверджує коректність реалізації логічної ізоляції даних через `organization_id`.

### 4.6. Тестування frontend-частини

Для frontend-частини виконано перевірку збірки Next.js застосунку командою `npm run build`. Успішна збірка підтверджує коректність TypeScript-коду, валідність імпортів, працездатність маршрутизації та відсутність критичних помилок компіляції.

Окрім цього, вручну перевірено такі сторінки:

- сторінка входу;
- сторінка реєстрації організації;
- сторінка прийняття запрошення;
- список заявок;
- сторінка створення заявки;
- сторінка деталей заявки;
- блок вкладень;
- сторінка управління користувачами.

Під час перевірки оцінювались наявність loading-станів, повідомлень про помилки, рольово-залежне відображення кнопок, коректність переходів між сторінками та правильність передачі JWT у запитах до backend.

### 4.7. Тестування backend-частини

Для backend-частини виконано запуск автоматичних тестів командою `go test ./...`. Тести проходять успішно, що підтверджує базову коректність збірки backend-проєкту та наявних модульних перевірок.

Окремо реалізовано тестування механізму перевірки вкладень на прикладі scanner-компонента. Це дозволяє перевірити, що потенційно небезпечний файл може бути відхилений до остаточного збереження в системі.

Надалі доцільно розширити автоматичне тестування такими групами тестів:

- тести автентифікації;
- тести статусних переходів заявки;
- тести role-based доступу;
- тести multi-tenant ізоляції;
- тести API вкладень;
- тести створення та прийняття запрошень користувачів.

### 4.8. Розгортання та дослідна експлуатація

Для локальної дослідної експлуатації система може запускатися у вигляді двох окремих застосунків: backend API та frontend Next.js. Backend підключається до PostgreSQL, отримує конфігурацію через environment variables і відкриває REST API. Frontend отримує адресу backend через змінну `NEXT_PUBLIC_API_URL`.

Для цільового розгортання передбачено таку схему:

- frontend - Vercel;
- backend - Render Web Service;
- база даних - Neon PostgreSQL або інший PostgreSQL-сумісний сервіс;
- файлове сховище - локальна файлова система для розробки, Cloudflare R2 як перспективний production-варіант.

Під час розгортання важливо не зберігати секрети в репозиторії. Значення `DATABASE_URL`, `JWT_SECRET`, параметри підключення до бази даних та інші конфіденційні змінні мають задаватися через панелі Environment Variables відповідних сервісів.

### Висновки до розділу 4

У четвертому розділі описано тестування та дослідну експлуатацію вебсистеми TicketFlow. Перевірено основні функціональні сценарії, рольове розмежування доступу, багатоклієнтність, роботу з вкладеннями, захист від несанкціонованого доступу та коректність збірки backend і frontend частин.

Результати тестування свідчать, що реалізована система відповідає ключовим вимогам дипломного проєкту: забезпечує створення та опрацювання заявок, підтримує рольову модель доступу, ізолює дані організацій, дозволяє працювати з вкладеннями та відображає стан SLA з урахуванням робочого календаря і паузових статусів. Подальше вдосконалення системи може бути пов'язане з розширенням автоматичного тестування, реалізацією production-сховища файлів та розвитком аналітичних функцій.

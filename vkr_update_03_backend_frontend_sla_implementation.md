# Оновлення 3: програмна реалізація SLA-engine

Цей файл містить фрагменти для розділу 3 фінальної ВКР. Основна заміна потрібна в підрозділах 3.1, 3.3 і 3.8.

## 1. Підрозділ 3.1 «Реалізація серверної частини»

### Що змінити

У поточному тексті модель `Ticket` описує SLA через `created_at`, `resolved_at` і пріоритет. Це потрібно замінити на опис SLA-engine.

### Готовий фрагмент

Модель `Ticket` описує заявку клієнта та містить такі основні поля: заголовок, опис, статус, пріоритет, автор, організація, можливий виконавець, дата створення, дата вирішення та дата оновлення. Для контролю SLA використовуються часові мітки `created_at`, `resolved_at`, пріоритет заявки та історія зміни статусів. SLA-engine обчислює активний час виконання не як просту різницю між датами, а з урахуванням робочого календаря, вихідних днів, святкових дат і паузових статусів.

Для фіксації історії зміни станів заявки використовується модель `TicketStatusHistory`. Вона зберігає попередній статус, новий статус, користувача, який виконав зміну, та час зміни. Наявність такої історії підвищує прозорість опрацювання заявок і дозволяє обґрунтовано розраховувати активний час виконання звернення в межах SLA.

## 2. Підрозділ 3.3 «Реалізація управління заявками»

### Що змінити

Потрібно прибрати формулювання про «базовий MVP» із п'ятьма статусами, бо фактична реалізація вже використовує розширений життєвий цикл.

### Готовий фрагмент

Життєвий цикл заявки обмежується визначеними переходами між статусами. У системі використовуються статуси `New`, `In Progress`, `Pending`, `Waiting for Customer`, `On Hold`, `Resolved`, `Closed` і `Reopened`. Перехід до нового статусу виконується лише після перевірки поточного стану заявки, ролі користувача та допустимості цільового статусу.

Статуси `New`, `In Progress` і `Reopened` вважаються активними для SLA, оскільки в цих станах заявка потребує опрацювання сервісною командою. Статуси `Pending`, `Waiting for Customer` і `On Hold` призупиняють SLA-лічильник. Вони використовуються тоді, коли подальше виконання залежить від додаткової інформації, відповіді клієнта або зовнішнього фактора. Статуси `Resolved` і `Closed` завершують активне опрацювання.

У разі переходу в статус `Resolved` встановлюється поле `resolved_at`, яке фіксує момент вирішення заявки. При повторному відкритті заявки через статус `Reopened` поле `resolved_at` очищується, оскільки заявка починає новий цикл опрацювання. При цьому дата створення `created_at` не змінюється, що дозволяє зберігати історичну цілісність звернення.

## 3. Підрозділ 3.8 «Реалізація контролю SLA»

### Повна заміна підрозділу

Контроль SLA у системі реалізовано як окремий backend-механізм `SLA Engine`. Його призначення полягає в тому, щоб визначати допустимий строк опрацювання заявки не лише за різницею між `created_at` і `resolved_at`, а з урахуванням робочого календаря та життєвого циклу звернення.

Для кожної заявки визначається граничний час виконання залежно від пріоритету:

- `High` — 8 робочих годин;
- `Medium` — 24 робочі години;
- `Low` — 72 робочі години.

Значення цих лімітів задаються через змінні середовища backend-застосунку. Це дозволяє адаптувати SLA-політику без зміни програмного коду. Також через конфігурацію задаються часовий пояс, початок і завершення робочого дня та перелік святкових дат. Типова конфігурація використовує часовий пояс `Europe/Kyiv` і робочий інтервал `09:00-18:00`.

SLA-engine працює з історією статусів заявки. Для кожного інтервалу між двома сусідніми змінами статусу визначається, чи був цей інтервал активним для SLA, чи паузовим. Активними є статуси `New`, `In Progress` і `Reopened`. Паузовими є `Pending`, `Waiting for Customer` і `On Hold`. Якщо інтервал припадає на неробочий час, вихідний або святковий день, він не збільшує активний SLA-час.

У результаті розрахунку backend формує такі SLA-показники:

| Поле API | Призначення |
| --- | --- |
| `sla_limit_seconds` | Загальний SLA-ліміт за пріоритетом заявки. |
| `active_duration_seconds` | Активний робочий час, витрачений на заявку. |
| `paused_duration_seconds` | Час, протягом якого заявка перебувала у паузових статусах. |
| `sla_remaining_seconds` | Залишок активного робочого часу до порушення SLA. |
| `sla_status` | Поточний стан SLA: `Within SLA`, `Paused`, `Met` або `Breached`. |
| `sla_due_at` | Прогнозований дедлайн виконання заявки. |
| `sla_breached_at` | Момент порушення SLA, якщо ліміт уже перевищено. |
| `sla_calendar_timezone` | Часовий пояс робочого календаря. |
| `sla_business_hours` | Робочий інтервал, який використовується для розрахунку. |

На frontend SLA відображається у двох рівнях деталізації. У списку заявок показується компактний індикатор стану SLA та співвідношення використаного активного часу до загального ліміту. На сторінці деталей заявки відображаються розширені показники: дедлайн, час паузи, робочий календар і час порушення SLA, якщо заявка вийшла за межі допустимого строку.

Такий підхід робить контроль SLA ближчим до реальних Helpdesk-систем, оскільки враховує не лише факт створення та вирішення заявки, а й робочий графік сервісної команди, паузи очікування та зміну станів у процесі опрацювання.

## 4. Конфігурація SLA-engine

У тексті розділу 3 або в описі розгортання варто зазначити такі змінні середовища:

| Змінна | Призначення |
| --- | --- |
| `SLA_TIMEZONE` | Часовий пояс робочого календаря, наприклад `Europe/Kyiv`. |
| `SLA_BUSINESS_START` | Початок робочого дня у форматі `HH:MM`. |
| `SLA_BUSINESS_END` | Завершення робочого дня у форматі `HH:MM`. |
| `SLA_HOLIDAYS` | Перелік святкових дат у форматі `YYYY-MM-DD`, розділених комами. |
| `SLA_HIGH_HOURS` | SLA-ліміт для високого пріоритету в робочих годинах. |
| `SLA_MEDIUM_HOURS` | SLA-ліміт для середнього пріоритету в робочих годинах. |
| `SLA_LOW_HOURS` | SLA-ліміт для низького пріоритету в робочих годинах. |

Якщо ці змінні не задано, backend використовує безпечні значення за замовчуванням: `Europe/Kyiv`, `09:00-18:00`, без святкових дат, 8/24/72 робочі години для пріоритетів `High`, `Medium` і `Low`.

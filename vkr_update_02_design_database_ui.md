# Оновлення 2: проєктування архітектури, бази даних та інтерфейсу

Цей файл містить фрагменти для розділу 2 фінальної ВКР. Їх потрібно використати там, де поточний текст описує SLA лише через часові мітки `created_at` і `resolved_at`.

## 1. Підрозділ 2.1 «Розробка архітектури програмної системи»

### Що змінити

У загальному описі архітектури потрібно додати SLA-engine як окремий backend-компонент бізнес-логіки.

### Готовий фрагмент

У backend-частині системи окремо виділено механізм SLA-engine, який відповідає за розрахунок строків виконання заявок. Він не є окремим мікросервісом, а реалізований як внутрішній модуль Go-застосунку, що використовується HTTP-обробниками під час формування відповіді щодо заявки. Такий підхід відповідає обраній монолітній архітектурі MVP, але водночас розділяє відповідальність між HTTP-рівнем, repository-рівнем і бізнес-логікою розрахунку SLA.

SLA-engine отримує дані про заявку, її пріоритет, історію статусів і поточний час. На основі цих даних модуль обчислює активний робочий час, час паузи, залишок SLA, прогнозований дедлайн і поточний SLA-статус. Конфігурація робочого календаря задається через змінні середовища, що дозволяє адаптувати систему до різних організаційних умов без зміни програмного коду.

## 2. Підрозділ 2.2 «Проєктування інтерфейсу користувача та користувацького досвіду»

### Що змінити

У поточному UI-описі є згадка про індикацію SLA. Її потрібно розширити, бо frontend тепер отримує з backend не лише статус, а й деталізовані SLA-показники.

### Готовий фрагмент

Для заявок у списку передбачено компактний SLA-індикатор, який показує поточний стан виконання: заявка перебуває в межах SLA, SLA призупинено, SLA виконано або SLA порушено. На сторінці детального перегляду заявки користувач отримує розширену інформацію: активний час опрацювання, граничний ліміт за пріоритетом, час паузи, залишок SLA, прогнозований дедлайн, момент порушення SLA та параметри робочого календаря.

Такий підхід дозволяє оператору або інженеру швидко оцінити критичність заявки без ручного аналізу історії статусів. Для клієнта SLA-індикатор підвищує прозорість процесу опрацювання звернення, оскільки показує, чи виконується заявка в межах визначених строків.

## 3. Підрозділ 2.4 «Проєктування структури бази даних»

### Що змінити

У моделі даних потрібно точніше пояснити роль `TicketStatusHistory`. Саме ця таблиця дозволяє SLA-engine відрізняти активний час від пауз.

### Готовий фрагмент

Для підтримки SLA-engine у структурі бази даних використовується таблиця історії статусів заявки `ticket_status_histories`. Вона зберігає ідентифікатор заявки, користувача, який виконав зміну, попередній статус, новий статус і час переходу. На основі послідовності таких записів система визначає інтервали, протягом яких заявка перебувала в активних або паузових станах.

Модель `Ticket` зберігає поточний статус, пріоритет, дату створення та дату вирішення. Пріоритет визначає SLA-ліміт, а дата вирішення використовується для завершення циклу опрацювання. При цьому сам розрахунок SLA не зводиться до різниці між `created_at` і `resolved_at`, оскільки кінцеве значення активного часу формується на основі статусної історії та робочого календаря.

У поточній реалізації політики SLA задаються через конфігурацію backend-середовища. Це спрощує MVP-реалізацію та не ускладнює структуру бази даних додатковими довідниковими таблицями. У подальшому розвитку системи ці правила можуть бути винесені в окрему таблицю `sla_policies`, якщо виникне потреба налаштовувати різні SLA-політики для окремих організацій, договорів або типів послуг.

## 4. Рекомендація для ER-діаграми

Якщо у фінальній ВКР є ER-діаграма, її можна залишити без окремої таблиці SLA-політик, але потрібно явно показати або описати такі поля та зв'язки:

| Елемент | Пояснення |
| --- | --- |
| `tickets.priority` | Визначає SLA-ліміт за конфігураційною політикою. |
| `tickets.status` | Визначає поточний стан SLA: активний, паузовий або фінальний. |
| `tickets.created_at` | Початкова точка життєвого циклу заявки. |
| `tickets.resolved_at` | Момент вирішення заявки. |
| `ticket_status_histories` | Джерело даних для розрахунку активних і паузових інтервалів. |

## 5. Рекомендація для UML/архітектурної діаграми

У backend-блоці доцільно додати внутрішній компонент:

`SLA Engine`

Його зв'язки:

- отримує `Ticket` і `TicketStatusHistory` з repository-рівня;
- використовує конфігурацію робочого календаря;
- повертає SLA-показники до ticket handler;
- не зберігає самостійно дані в БД.

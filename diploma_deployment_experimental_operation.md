# Розгортання та дослідна експлуатація вебсистеми TicketFlow

## 1. Загальна характеристика етапу розгортання

Після завершення основної реалізації вебсистеми TicketFlow було визначено схему її розгортання у хмарному середовищі. Метою цього етапу є перевірка працездатності системи поза локальним середовищем розробки, а також підтвердження того, що окремі компоненти можуть взаємодіяти між собою через мережу відповідно до обраної архітектури.

Система TicketFlow побудована як вебзастосунок із розділенням на клієнтську та серверну частини. Frontend реалізовано на основі Next.js, backend побудовано як REST API мовою Go, а для збереження даних використовується PostgreSQL. Такий підхід дає змогу розгортати компоненти незалежно один від одного, що спрощує супровід системи, оновлення окремих частин і подальше масштабування.

Для дослідного розгортання було обрано хмарні сервіси, які достатні для перевірки MVP-версії системи та не потребують складної інфраструктурної підготовки. Frontend-частина може бути розгорнута на платформі Vercel, backend-частина - як Web Service на Render, база даних - у Neon PostgreSQL, а зберігання вкладень у production-середовищі може виконуватися за допомогою Cloudflare R2 як S3-сумісного об'єктного сховища.

## 2. Схема розгортання компонентів

Архітектура розгортання TicketFlow передбачає логічне розділення основних компонентів системи:

| Компонент | Технологія | Середовище розгортання | Призначення |
| --- | --- | --- | --- |
| Frontend | Next.js, React, TypeScript | Vercel | Відображення інтерфейсу користувача |
| Backend | Go, Gin, GORM | Render Web Service | Обробка REST API-запитів і бізнес-логіки |
| Database | PostgreSQL | Neon PostgreSQL | Збереження організацій, користувачів, заявок, коментарів і метаданих вкладень |
| File storage | Cloudflare R2 або local storage | R2 для production, локальна файлова система для розробки | Збереження файлів вкладень |

У такій схемі frontend не звертається безпосередньо до бази даних або файлового сховища. Усі операції виконуються через backend API, який відповідає за автентифікацію користувача, перевірку ролі, контроль належності даних до організації та виконання бізнес-правил. Це важливо з погляду безпеки, оскільки клієнтська частина не отримує прямого доступу до внутрішніх ресурсів системи.

Взаємодія між frontend і backend здійснюється через HTTP-запити до REST API. Базова адреса backend-сервісу задається у frontend через змінну середовища `NEXT_PUBLIC_API_URL`. Для захищених запитів frontend додає JWT-токен у заголовок `Authorization` у форматі `Bearer <token>`.

## 3. Розгортання backend-частини

Backend-частина TicketFlow розгортається як окремий Web Service. Для цього використовується Go-застосунок, точкою входу якого є пакет у директорії `cmd`. Під час розгортання сервіс виконує збірку застосунку та запускає скомпільований виконуваний файл.

Приклад команди збірки:

```bash
go build -o ticketflow ./cmd
```

Приклад команди запуску:

```bash
./ticketflow
```

Конфігурація backend-застосунку виконується через змінні середовища. Такий підхід є доцільним, оскільки секретні параметри не зберігаються в репозиторії та можуть змінюватися без модифікації програмного коду.

Основні змінні середовища backend-частини:

| Змінна | Призначення |
| --- | --- |
| `DATABASE_URL` або параметри підключення до БД | Підключення до PostgreSQL |
| `JWT_SECRET` | Секретний ключ для підпису JWT |
| `JWT_TTL_HOURS` | Тривалість дії JWT у годинах |
| `PORT` або `SERVER_PORT` | Порт запуску backend-сервісу |
| `GIN_MODE` | Режим роботи Gin |
| `FRONTEND_ORIGIN` | Дозволене джерело запитів для CORS |
| `STORAGE_PROVIDER` | Тип файлового сховища: `local` або `r2` |
| `LOCAL_STORAGE_DIR` | Локальна директорія для файлів у середовищі розробки |
| `R2_ENDPOINT`, `R2_BUCKET`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY` | Параметри підключення до Cloudflare R2 |

Під час запуску backend встановлює з'єднання з базою даних, ініціалізує маршрути API та middleware автентифікації. Для MVP-версії допускається використання AutoMigrate, якщо така логіка вже передбачена в коді. У подальшому для production-середовища доцільно перейти до контрольованих міграцій бази даних, оскільки вони краще підходять для відстеження змін схеми.

## 4. Розгортання frontend-частини

Frontend-частина TicketFlow розгортається окремо від backend. Для цього використовується платформа Vercel, яка добре підтримує Next.js-застосунки. У випадку monorepo для frontend необхідно вказати кореневу директорію `ticketflow-web`.

Перед розгортанням frontend виконується production-збірка:

```bash
npm run build
```

Збірка перевіряє коректність TypeScript-коду, структуру сторінок Next.js і можливість генерації production-версії застосунку. Якщо збірка завершується успішно, застосунок може бути опублікований у Vercel.

Ключовою змінною середовища frontend-частини є:

```env
NEXT_PUBLIC_API_URL=https://<backend-service>.onrender.com/api/v1
```

Ця змінна визначає адресу backend API, до якого звертається клієнтська частина. Її значення має відрізнятися для локального середовища та для розгорнутого застосунку. У локальній розробці зазвичай використовується адреса на кшталт `http://localhost:8080/api/v1`, тоді як у production-середовищі вказується URL сервісу Render.

## 5. Розгортання бази даних

Для збереження структурованих даних системи використовується PostgreSQL. У дослідній схемі розгортання може застосовуватися Neon PostgreSQL, який надає керований екземпляр бази даних і дозволяє підключатися до нього через захищений connection string.

У базі даних зберігаються такі основні групи даних:

- організації;
- користувачі;
- заявки;
- коментарі до заявок;
- історія статусів;
- метадані вкладень.

Важливо, що binary-вміст файлів не зберігається у PostgreSQL. База даних містить лише метадані вкладень, зокрема назву файлу, розмір, MIME-тип, ідентифікатор заявки та ключ зберігання. Такий підхід зменшує навантаження на базу даних і краще відповідає практиці побудови вебсистем, у яких файли зберігаються в окремому файловому або об'єктному сховищі.

## 6. Організація зберігання вкладень

У локальному середовищі розробки вкладення можуть зберігатися у файловій системі, наприклад у директорії `uploads`. У production-середовищі доцільно використовувати Cloudflare R2 як S3-сумісне об'єктне сховище. Це дає змогу відокремити зберігання файлів від життєвого циклу backend-сервісу.

Логічний ключ вкладення має структуру:

```text
attachments/{orgID}/{ticketID}/{attachmentID}_{originalFileName}
```

Для локального сховища цей ключ може відповідати файловому шляху:

```text
uploads/{orgID}/{ticketID}/{attachmentID}_{originalFileName}
```

Такий формат ключа дозволяє логічно групувати файли за організацією та заявкою. Це спрощує адміністрування вкладень і підтримує загальну модель багатоклієнтності.

Доступ до файлів не надається через публічні посилання. Завантаження вкладення виконується через backend endpoint, який перед поверненням файлу перевіряє JWT-токен, роль користувача, організацію, належність заявки та відповідність вкладення конкретній заявці. Такий підхід є безпечнішим, оскільки рішення про доступ до файлу приймається серверною частиною системи.

## 7. Налаштування CORS та безпеки взаємодії

Оскільки frontend і backend можуть бути розгорнуті на різних доменах, у backend-частині необхідно налаштувати CORS. Значення дозволеного джерела запитів задається через змінну `FRONTEND_ORIGIN`. У production-середовищі вона має відповідати домену frontend-застосунку у Vercel.

Для захищених операцій використовується JWT-автентифікація. Після успішного входу користувач отримує токен, який frontend зберігає і додає до наступних запитів. Backend перевіряє підпис токена, строк його дії, роль користувача, організацію та версію токена. Механізм `token_version` дозволяє відкликати попередньо видані токени користувача після зміни критичних параметрів, наприклад ролі.

У разі завершення строку дії JWT або його відкликання backend повертає відповідь `401 Unauthorized`. Frontend обробляє таку ситуацію централізовано: очищує локальні дані автентифікації та перенаправляє користувача на сторінку входу. Якщо користувач намагається відкрити заявку, до якої не має доступу, або неіснуючу заявку, клієнтська частина перенаправляє його до списку заявок, не розкриваючи зайвих деталей про причину відмови.

## 8. Дослідна експлуатація системи

Дослідна експлуатація TicketFlow передбачає перевірку основних бізнес-сценаріїв після розгортання системи. Її метою є підтвердження того, що застосунок коректно працює в умовах, наближених до реального використання, а окремі компоненти взаємодіють між собою відповідно до проєктної архітектури.

Під час дослідної експлуатації доцільно перевірити такі сценарії:

| Сценарій | Очікуваний результат |
| --- | --- |
| Реєстрація або створення користувача | Користувач створюється в межах організації |
| Вхід у систему | Користувач отримує JWT і переходить до списку заявок |
| Створення заявки клієнтом | Заявка створюється зі статусом `New` |
| Перегляд списку заявок | Користувач бачить лише дозволені йому заявки |
| Зміна статусу заявки | Дозволені переходи виконуються згідно з роллю |
| Додавання коментаря | Коментар зберігається і відображається в історії заявки |
| Завантаження вкладення | Файл проходить перевірку формату, розміру та прав доступу |
| Скачування вкладення | Файл повертається лише авторизованому користувачу з відповідними правами |
| Завершення строку дії JWT | Користувача перенаправляє на сторінку входу |
| Спроба доступу до чужої заявки | Доступ блокується, дані не розкриваються |

Під час перевірки особливу увагу потрібно приділити багатоклієнтності. Користувач однієї організації не повинен бачити заявки, коментарі або вкладення іншої організації. Для клієнта додатково перевіряється обмеження доступу лише до власних заявок.

## 9. Результати дослідної експлуатації

За результатами дослідної експлуатації можна зробити висновок, що обрана архітектура є придатною для MVP-версії вебсистеми управління запитами клієнтів у сервісі з надання IT-послуг. Розділення frontend, backend, бази даних і файлового сховища дозволяє незалежно налаштовувати та оновлювати окремі компоненти.

Перевірка основних сценаріїв підтверджує працездатність ключових функцій системи: автентифікації, створення та перегляду заявок, зміни статусів, роботи з коментарями, контролю доступу за ролями та обробки вкладень. Окремо підтверджується, що система не покладається лише на frontend-перевірки, а виконує контроль доступу на backend-рівні.

Дослідна експлуатація також показує, що система може бути розширена в майбутньому. Зокрема, можливими напрямами розвитку є додавання розширеної аналітики, формування звітів, розширення SLA-engine окремими договірними політиками для різних типів послуг, інтеграція з зовнішнім об'єктним сховищем у production-середовищі та впровадження повноцінної системи міграцій бази даних.

## 10. Висновок до розділу

Розгортання та дослідна експлуатація TicketFlow підтверджують, що реалізована система може функціонувати як цілісний вебзастосунок із розділеною клієнтською та серверною частинами. Використання Vercel, Render, Neon PostgreSQL і Cloudflare R2 відповідає потребам MVP-версії та дозволяє перевірити роботу системи в хмарному середовищі без розгортання складної власної інфраструктури.

Реалізована схема забезпечує базові вимоги до безпеки та надійності: секретні параметри зберігаються у змінних середовища, доступ до API захищено JWT, дані організацій ізольовано через `organization_id`, а робота з вкладеннями виконується через backend із перевіркою прав доступу. Це створює основу для подальшого розвитку системи та її адаптації до ширшого використання в межах IT-сервісу.
